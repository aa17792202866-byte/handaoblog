2. 必背理论知识

2.1 软件、软件测试与缺陷 ★★★★★

软件 = 程序 + 数据 + 文档。软件测试是使用人工或自动化手段对被测对象进行测试操作，检查实际结果与预期结果是否存在差异。

  • 测试对象不仅是可执行程序，也包括数据、需求、设计、安装手册、用户文档等。
  • 测试目的：发现被测对象与用户需求之间的差异；了解质量状况并为决策提供依据；积累经验并预防缺陷；降低产品失败风险。
  • 关键词：人工或自动化、被测对象、实际结果、预期结果、差异。
  • 易错点：测试能证明缺陷存在，却不能证明软件完全没有缺陷。

缺陷判定五条：

  1. 需求要求的功能没有实现。
  2. 出现了需求明确指出不应出现的错误。
  3. 实现了需求没有要求的功能。
  4. 需求没有明说，但合理、必要的隐含功能没有实现。
  5. 软件难理解、不易使用、运行缓慢，或用户体验明显不好。

来源： 0、软件与软件测试概述.pptx、3、软件测试基础-软件测试入门V2.0.pptx、软件测试基础作业。

2.2 软件测试七项原则 ★★★★☆

原则 一句话答案 做题关键词
测试证明缺陷存在 测试只能降低漏测风险，不能证明不存在缺陷 不能证无错
尽早测试 缺陷发现越早，修复成本越低 早介入、评审
穷尽测试不可能 输入、路径和环境组合过多，应按风险选重点 风险、优先级
缺陷群集 少数复杂或重要模块往往集中多数缺陷 二八原理
杀虫剂悖论 重复同一组用例会逐渐失效，应定期评审和更新 更新用例
测试依赖背景 不同业务、目标和风险需要不同测试策略 因项目而异
不存在缺陷的谬论 没发现 Bug 但不能满足用户需求，产品仍然失败 用户价值

来源： 3、软件测试基础-软件测试入门V2.0.pptx、韩瑞轩软件测试基础-day03作业.txt。

2.3 软件生命周期和测试阶段 ★★★★☆

软件生命周期：计划 → 需求分析 → 设计 → 编码 → 测试 → 运行维护。主要产物依次包括项目计划、SRS、HLD/LLD、源程序与数据库、测试产物、运行版本与维护记录。

测试阶段 对象/重点 依据 典型方法
单元测试 UT 最小程序单元、内部逻辑 详细设计说明书 LLD 白盒
集成测试 IT 模块接口、数据传递和组合功能 概要设计说明书 HLD 灰盒
系统测试 ST 完整系统对需求的符合度 需求规格说明书 SRS 黑盒
验收测试 AT 成品是否满足用户/合同要求 合同、SRS、验收计划 用户主导
  • α：用户在开发环境或内部模拟环境测试，开发人员在场，环境受控。
  • β：多个真实用户在实际环境测试，开发人员通常不在现场，环境不可控。
  • UAT：终端用户或利益相关方验证系统是否可接受，也可能依据法规和行业标准。

来源： 1、软件生命周期V2.0.pptx、4、软件测试基础-测试阶段V2.0(!).pptx。

2.4 测试分类 ★★★★☆

划分依据 分类 核心区别
是否关注内部结构 黑盒、白盒、灰盒 黑盒看输入输出；白盒看代码结构；灰盒兼顾外部行为和内部信息
是否运行被测对象 静态、动态 静态不运行，如评审；动态实际运行并比较结果
执行方式 手工、自动化 人工操作与判断；工具或脚本自动执行
  • 黑盒又称基于规格说明的测试、数据驱动测试。
  • 白盒又称结构测试、逻辑驱动测试。
  • 灰盒典型场景是集成测试、接口测试，常借助日志、接口灌数、打桩。
  • 自动化适合重复、稳定、高频的冒烟和回归，也适合性能等人工难以完成的测试；它依赖测试设计和软件稳定性，不能完全替代人工探索与体验判断。

来源： 5、软件测试基础 - 测试方法v2.0(!).pptx。

2.5 测试模型 ★★★☆☆

模型 核心 优点 局限
V 模型 开发阶段与测试级别对应 阶段清楚，覆盖底层到高层 早期缺陷可能到后期才发现，变更返工大
W 模型 测试与研发并行，测试需求和设计文档 尽早介入，测试对象含程序和文档 技术与组织要求较高
敏捷测试 短迭代、持续测试、持续反馈 响应变化快，质量责任共享 需要紧密协作与持续调整

来源： 6、软件测试模型V2.0.pptx、2、软件研发模型V2.0.pptx。

2.6 系统测试类型 ★★★★☆

类型 核心检查点
功能测试 功能是否正确、完整、符合明确及隐含需求；输入输出和业务流程是否正确
性能测试 响应时间、成功率、CPU、内存、磁盘、并发量
负载测试 在不同负载下观察性能，找到临界点
压力测试 在超负荷或恶劣条件下寻找薄弱点、极限及恢复能力
容量测试 最大用户数、连接数、数据量、文件量等容量
稳定性测试 一定负载下长时间运行，关注泄漏、数据不一致和性能下降
安全性测试 登录、权限、加密、完整性、日志、身份认证、越权
兼容性测试 操作系统、浏览器、硬件、分辨率、网络、第三方软件
GUI / 可用性 与设计一致、美观统一；易识别、易学习、易操作、错误提示清楚
异常测试 断网、宕机、资源不足等异常下的容错、排错和恢复
文档测试 文档正确、完整、一致，步骤可执行
安装卸载测试 安装前/中/后、异常安装、日志、卸载后重装
接口测试 系统/模块之间的数据交换、传递、控制及逻辑依赖

可靠性常用指标：MTBF = 总工作时间 ÷ 总失效次数，数值越大通常表示越可靠。

来源： 7、系统测试类型v2.0.pptx。

3. 项目实战理论题重点

🔥 老师最新资料重点　来源：项目实战理论题.txt，并结合测试流程课件、作业和测试用例表格补全。

3.1 软件测试流程是什么？ ★★★★★

标准答案：

  1. 需求评审：确认 SRS 完整、准确、可测试，各角色理解一致。
  2. 测试计划：确定范围、人员、资源、进度、标准和交付物。
  3. 测试设计：进行测试需求分析，确定测试项/子项，编写测试方案。
  4. 测试实现：分析模块、提取测试点、编写并评审用例、准备数据、搭建环境。
  5. 测试执行：版本提测后先冒烟；通过后执行用例、记录结果、提交和跟踪缺陷、回归。
  6. 测试收尾：达到准出标准后统计数据、评估质量、处理遗留缺陷并提交测试报告。

关键词： 需求评审、计划、需求分析、方案、用例、环境、冒烟、执行、缺陷、回归、报告。

速记： 评需求 → 定计划 → 析需求/定方案 → 写用例/搭环境 → 冒烟/执行/缺陷/回归 → 报告。

可能的变体问法： 各阶段产物是什么？答：需求评审表、测试计划、测试方案/思维导图、测试用例、缺陷报告、测试总结报告。

3.2 需求评审怎么做？关注什么？ ★★★★★

标准答案： 产品、项目、开发、测试等相关人员参加；先发评审通知和材料，各角色预审并记录问题，再召开会议讨论；产品负责人确认结论并修改，最后跟踪问题闭环。测试人员要确认自己理解无疑问，确认文档能指导测试，并对不合理、不可测处提出建议。

关注点： 完整性、一致性、可行性、正确性；还应检查明确性、可测试性、边界/异常、角色权限、业务流程、数据规则、性能安全等非功能要求。

速记： 先预审，后开会；查“完、一、可、正”，问题要闭环。

3.3 用例评审怎么做？评审什么？ ★★★★★

标准答案： 测试人员完成用例后组织产品、开发、测试共同评审；逐条确认用例与需求的对应关系、覆盖、正确性和可执行性；记录意见，修改后复核关闭。

评审内容： 需求和测试点是否覆盖；正向、反向、边界、异常、流程和权限是否覆盖；前置条件、数据、步骤、预期是否清楚且可执行；优先级是否合理；用例是否重复、遗漏或相互矛盾。

速记： 覆盖全、写得对、跑得通、优先级合理、无重漏矛盾。

3.4 测试计划包含什么？ ★★★★★

标准答案： 测试目标和范围、资源准备（人员、软硬件、工具）、组织分工、工作安排与进度、风险、测试标准（准入/准出、挂起/恢复、通过/失败）、交付物。

速记： 范围、资源、人员、进度、风险、标准、交付物。

3.5 准入和准出标准是什么？ ★★★★★

准入标准：

  1. 测试用例已编写并评审完成。
  2. 开发人员已提交提测单及相关配置文档、程序和数据库脚本。
  3. 冒烟测试通过（要求 100% 通过）。
    准出标准：通常和准入标准一致

准入示例： 需求已基线；用例已编写并评审；开发提交提测单、版本、配置和数据库脚本；测试环境和数据就绪；冒烟用例 100% 通过。

准出/通过示例： 需求覆盖率和计划用例执行率达到约定目标；致命、严重缺陷全部解决；一般和轻微缺陷达到项目约定解决率或已有获批的遗留方案；无阻塞发布的问题；测试报告完成。

易错点： 资料作业写有“用例执行率达到 100% 及以上”，正确上限是 **100%**。资料中的“严重缺陷 100%，一般/轻微 95%”属于示例阈值，考试若给定项目标准，应按题目作答。

3.6 测试通过和失败标准是什么？ ★★★★★

通过： 达到项目约定的需求覆盖、用例执行与通过标准；关键缺陷关闭；遗留风险获确认；没有影响发布的阻塞问题。

失败： 任一强制标准未达到，如冒烟失败、关键流程不通、致命/严重缺陷未关闭、执行或覆盖不足、遗留风险不可接受。

速记： 通过看覆盖、执行、缺陷、风险；硬指标不达即失败。

3.7 挂起和恢复标准是什么？ ★★★★★

挂起： 需求频繁或重大变更；版本质量过差/冒烟失败；阻塞缺陷使测试无法继续；环境、数据或关键设备不可用；出现更高优先级任务。

恢复： 需求稳定；新版本主要流程通过冒烟；阻塞缺陷已修复；环境和数据恢复；高优任务完成并重新具备测试资源。

速记： 需求、版本、环境、资源不具备就挂起；问题解除并复验后恢复。

3.8 测试方案包含什么？用了哪些设计方法？ ★★★★★

标准答案： 测试环境、测试范围和重点、测试类型/维度、测试方法、测试数据和工具、执行策略、用例优先级标准、缺陷严重级别标准。

项目举例： 商城注册用等价类和边界值覆盖用户名 3～10 位、密码 6～15 位、手机号 11 位；外卖优惠组合用判定表；订单和请假状态用状态迁移/场景法；多条件查询用正交法；登录历史高发问题用错误推测法。

速记： 方案回答“怎么测”；计划回答“谁在何时用什么资源测什么”。

3.9 测试报告包含什么？测试结论怎么写？ ★★★★★

标准答案： 实际测试环境和版本、测试范围、测试过程数据及分析、需求覆盖和用例执行情况、缺陷统计与趋势、遗留缺陷及风险、版本质量评估、后续建议、测试结论。

结论模板： “本轮完成约定范围测试，核心业务流程通过，致命/严重缺陷已关闭，现存一般/轻微缺陷及影响为……。根据准出标准，本版本【通过/有条件通过/不通过】测试，建议【发布/修复后回归/暂缓发布】。”

3.10 合格测试用例有哪些要素？ ★★★★★

标准答案： 测试项、测试子项、用例 ID、用例标题、测试类型、重要级别/优先级、预置条件、测试数据、步骤描述、预期结果；执行时还记录轮次、实际结果、执行人、时间和备注，并关联需求与缺陷。

速记： 编号标题定身份，前置数据备条件，步骤预期可执行，优先类型便管理。

3.11 用例优先级如何划分？ ★★★★★

优先级 资料口径 项目例子
高 核心功能正向用例 正常登录、下单支付、订单主状态流转
中 核心功能反向；次要功能正向 密码错误、余额不足、取消订单
低 次要功能反向、易用性、容错和低风险异常 非关键提示文字、少见显示问题

易错点： 用例优先级表示先执行什么；缺陷优先级表示先修复什么；缺陷严重程度表示影响有多大。

3.12 合格缺陷有哪些要素？ ★★★★★

标准答案： 产品/项目/模块、影响版本、标题、缺陷类型、严重程度、优先级、指派人、操作系统/浏览器、前置条件、复现步骤、实际结果、预期结果、复现概率、截图/录屏/日志等附件。接口缺陷还应写接口地址、请求方式、参数、响应和必要的请求头。

好标题： “位置 + 操作 + 实际问题”，一条缺陷只描述一个问题。描述遵循 5C：准确、清晰、简洁、完整、一致。

3.13 缺陷严重级别如何划分？ ★★★★★

级别 判定 示例
致命 系统崩溃、宕机、无法启动/登录、主流程完全阻断，测试无法继续 商城无法登录或支付系统整体不可用
严重 主要功能丧失、关键数据不能保存，服务明显受影响，但存在部分测试空间 支付成功但订单未生成
一般 次要功能错误或兼容问题，不影响主要流程继续 某浏览器图片不显示
轻微 文字、样式、美观、操作建议等低影响问题 错别字、轻微错位

Severity 与 Priority： Severity 看影响，Priority 看修复紧急度。首页错别字严重度低但发布前优先级可能高；极少触发的数据损坏严重度高，但若当前无法触发，修复排期可能由项目决定。

3.14 缺陷管理流程是什么？ ★★★★★

标准答案： 测试新建并指派 → 开发确认；不是缺陷则拒绝，是缺陷则打开 → 开发修复或延期 → 修复后标为已修复并指回测试 → 测试回归；通过则关闭，不通过则重新打开。

3.15 用例和缺陷是什么关联？ ★★★★★

标准答案： 用例指导执行并定义预期；实际结果与预期不一致时创建缺陷。缺陷应关联触发它的用例和需求，形成“需求 → 用例 → 执行 → 缺陷 → 回归”的可追踪链。一个用例可能发现多个缺陷，一个缺陷也可能影响多个用例。

3.16 开发不认可缺陷怎么办？ ★★★★★

标准答案： 先检查版本、环境、数据和步骤，补充截图、日志或录屏并稳定复现；与开发沟通事实和影响；对“设计如此”找产品/需求确认；对“无法复现”当面复现或补充条件；仍有分歧时在禅道记录双方依据，重新激活并请产品、测试负责人或项目负责人裁决。不要私下删除或关闭争议记录。

速记： 先自证，后沟通；需求找产品，技术找证据，分歧留记录并升级。

3.17 版本提测流程是什么？ ★★★★★

标准答案： 开发完成自测 → 提交提测单和版本包、变更说明、安装/配置说明、数据库脚本及已知问题 → 配置/部署到测试环境 → 测试核对版本和环境 → 执行冒烟 → 通过则正式测试，不通过则拒收并退回开发重提。

3.18 回归测试策略是什么？ ★★★★★

标准答案： 完全回归执行所有用例；选择性回归按变更影响、风险、核心流程和历史缺陷选择用例。资料给出的三轮策略：第一轮验证已修复缺陷；第二轮验证关联度高的功能；第三轮执行全部用例。

确认测试与回归： 确认测试看“原问题是否修好”；狭义回归看“修改是否引入新问题”。实际项目常统称回归测试。

3.19 冒烟测试策略是什么？ ★★★★★

标准答案： 对新版本的主要功能和主要业务流程做短时间预测试，判断版本是否可进入正式测试。老师资料要求冒烟用例 100% 通过；失败说明版本存在重大倒退，应退回开发重构版本。

3.20 为什么测试执行比用例设计时间长？ ★★★★★

标准答案： 用例通常只设计一次或按变更维护，而执行会跨多个版本和多轮重复；每轮还包括环境/数据准备、执行记录、缺陷复现与提交、开发沟通、修复验证、关联回归、兼容或多配置重复验证，以及阻塞等待。因此总执行工时通常大于一次设计工时。

速记： 设计一次，版本多轮；执行还带环境、数据、缺陷、回归和等待。

4. 测试用例设计方法

4.1 等价类划分法 ★★★★★

定义： 把输入域划分成若干内部行为相同的集合，每个集合选代表值测试；分为有效等价类和无效等价类。

适用： 有明确输入范围、长度、类型、格式、必填和取值集合的表单。

步骤： 提取每个输入条件 → 划分有效/无效等价类并编号 → 每个有效类至少选一个代表值 → 每个无效类通常单独成例，其他字段保持有效 → 写出预期结果。

资料案例：商城注册。 用户名有效类包括 3～10 位、中文/数字/字母、必填、不含空格；无效类包括少于 3 位、多于 10 位、空、纯空格、含空格、含符号。密码要求 6～15 位，数字/字母/符号至少两种。

易错点： 把一个用例同时放入多个无效条件，失败后无法判断原因；漏掉空值、纯空格；把边界点当成等价类的全部。

答题模板：

条件 有效等价类 代表值 无效等价类 代表值
用户名长度 3～10 位 abc 小于3；大于10 ab；11位字符

然后注明：“有效类可合理组合；无效类每次只改变一个条件，其他输入均合法。”

来源： 韩瑞轩的测试用例作业day1.xlsx。

4.2 边界值分析法 ★★★★★

定义： 缺陷容易集中在边界及其附近，重点选择最小值、最小值附近、最大值和最大值附近。

适用： 长度、数值、日期、数量、次数、容量等连续范围。

步骤： 找上下界 → 判断边界是否包含 → 取 min-1、min、min+1、max-1、max、max+1 → 加正常值 → 写预期。

资料案例： 用户名 3～10 位可取 2、3、4、9、10、11 位；密码 6～15 位可取 5、6、7、14、15、16 位；订单第二页每页 5 条的偏移量是 5。

易错点： 只测上下界，不测边界外；忽略“包含/不包含”；日期跨月和金额小数精度常被漏掉。

答题模板： “范围为 [a,b]，选择 a-1、a、a+1、b-1、b、b+1，分别验证拦截或接受及提示。”

4.3 判定表法 ★★★★★

定义： 把多个条件组合与对应动作整理成表，每一列规则形成一条用例。

适用： 多个布尔/枚举条件共同决定不同结果，组合逻辑复杂。

步骤： 列条件桩 → 列动作桩 → 枚举或约束条件组合 → 删除不可能/重复组合 → 为每条有效规则写用例。

资料案例：

  • 美团外卖：新/老顾客、是否使用优惠券、是否满足店铺满减、节日金额区间共同决定立减、优惠券、满减、八折/七折。
  • 用户删除：未选择、单条/批量、启用/禁用、确认/取消决定能否删除。
  • 快递计费与共享单车支付优先级也适合判定表。

易错点： 条件互斥却仍做笛卡尔组合；忘记动作顺序；未说明冲突优惠的优先规则。

答题模板： 先画“条件项/规则1…n”和“动作项/规则1…n”表，再说明“一列一用例”，补齐前置、数据、步骤和预期。

4.4 因果图法 ★★★☆☆

定义： 用图描述输入条件（因）与输出动作（果）的逻辑关系，再转换为判定表。

适用： 条件和结果多、存在与/或/非以及互斥、唯一、包含等约束。

步骤： 找原因和结果并编号 → 画逻辑关系和约束 → 转换成判定表 → 每条规则生成用例。

易错点： 因果图是分析工具，最后仍需落到可执行用例；不能遗漏条件之间的约束。

答题模板： “列因 C1…Cn 和果 E1…En，标注逻辑与约束，转判定表，按规则生成用例。”

来源： 2. 测试需求分析.pptx列出“判定表&因果图”；资料没有独立完整因果图案例，因此本节为补充理解。

4.5 场景法 / 流程分析法 ★★★★★

定义： 围绕用户完成业务的基本流和备选流设计端到端用例。

适用： 登录、支付、取款、下单、审批等有清晰业务流程的功能。

步骤： 画主流程 → 找每个节点的分支和异常 → 一条完整路径形成一个场景 → 覆盖基本流、各备选流及关键组合 → 检查数据和状态变化。

资料案例： ATM 正常取款为基本流；密码错误、卡无效、余额不足、金额超限、ATM 余额不足为备选流。共享单车支付按卡包 → 余额 → 红包 → 充值逐级判断。

易错点： 只测页面操作，不检查金额、库存、订单状态和日志；把零散步骤写成多个不完整用例。

答题模板： “基本流 A-B-C-D；备选流在节点 B/C 分支。为每条从起点到终点的有效路径设计用例，并验证界面、状态和数据一致性。”

4.6 状态迁移法 ★★★★★

定义： 根据对象当前状态、触发事件和下一状态设计合法及非法迁移测试。

适用： 订单、缺陷、审批、账户等状态明显的对象。

步骤： 列状态 → 列事件 → 画状态图/表 → 覆盖每条合法迁移 → 测关键非法迁移 → 验证状态、可用操作、历史记录。

资料案例： 订单 待付款 → 待发货 → 待收货 → 待评价 → 已完成；缺陷 新建 → 打开 → 已修复 → 关闭/重新打开；请假 草稿 → 待审批 → 通过/不通过。

易错点： 只覆盖正常状态；未验证非法跳转；只看页面标签而不查后台数据和历史记录。

答题模板： 写出“当前状态 + 事件 → 目标状态”，每条合法边一例，每条关键禁止边一例。

4.7 正交试验法 ★★★★☆

定义： 利用正交表从多因素、多水平组合中选出分布均匀、有代表性的组合，减少用例数。

适用： 参数很多、组合数爆炸，且希望覆盖各因素水平之间的代表性搭配。

步骤： 列因素和水平 → 计算最大水平数 → 选合适正交表 → 将因素映射到列 → 生成组合 → 补充业务必测、异常和全空组合。

资料案例： 组合查询有“姓名填/不填、账号填/不填、状态启用/禁用/不选、地点北京/上海/广州/西安/不选”，资料用代表组合生成 15 条用例。

易错点： 正交表不能自动覆盖边界、业务禁配和高风险组合；~填等临时标记要转成实际数据。

答题模板： 先列因素水平表，再列正交组合表，最后将每行改写成完整用例并补特殊组合。

4.8 错误推测法 ★★★☆☆

定义： 根据经验、历史缺陷和系统薄弱点推测容易出错的位置并设计用例。

适用： 需求不完整、已有同类缺陷、时间有限，需要补充其他方法覆盖不到的风险。

示例： 重复点击提交、返回后再次支付、断网重连、刷新导致重复订单、特殊字符、超长文本、并发修改、缓存状态不一致。

易错点： 只凭感觉，没有结合历史缺陷和业务风险；它应补充系统方法，不能完全替代等价类、边界或流程分析。

5. SQL 核心知识

资料范围： MySQL；重点来源为 数据库笔记day02～day05.txt、数据库作业、汇智云商SQL题目.txt和补充的数据库表字典。本章中的 member/goods/orders 等短表名只用于演示通用语法；第 6 章使用汇智云商真实表名。

5.1 基本执行顺序 ★★★★★

写题时按“需要哪些表 → 如何关联 → 行筛选 → 分组 → 组筛选 → 显示什么 → 排序 → 分页”思考。

5.2 条件、模糊、范围与空值 ★★★★★

  • %匹配 0 个或多个字符，_匹配恰好 1 个字符。
  • BETWEEN a AND b包含两端。
  • 空值用 IS NULL / IS NOT NULL，不能写 = NULL。
  • NULL与空字符串 ''不同。
  • AND优先于OR，复杂条件主动加括号。

5.3 去重、排序与分页 ★★★★★

  • 多字段 DISTINCT要求所选字段组合完全相同才去重。
  • 多字段排序先按第一字段，同值时才按第二字段。
  • MySQL：第 n 页、每页 m 条，LIMIT m * (n - 1), m。第二页每页 5 条即 LIMIT 5, 5。
  • 分页必须配稳定排序，否则不同执行间可能出现重复/遗漏。

5.4 聚合、分组和 HAVING ★★★★★

函数 含义 NULL 行为
COUNT(*) 统计结果行数 包含字段为 NULL 的行
COUNT(col) 统计该字段非 NULL 的行数 忽略 NULL
SUM/AVG(col) 求和/平均 忽略 NULL
MAX/MIN(col) 最大/最小 忽略 NULL
ROUND(n,d) 四舍五入到 d 位小数 —

WHERE筛选分组前的原始行，通常不能直接写聚合函数；HAVING筛选分组后的结果，可写聚合函数。

5.5 连接查询 ★★★★★

  • INNER JOIN只保留两边能匹配的行。
  • LEFT JOIN保留左表全部行，右表匹配不到的列补 NULL。
  • RIGHT JOIN保留右表全部行；通常交换表顺序改成更易读的 LEFT JOIN。
  • 查询“未匹配数据”：左连接后筛选右表主键为空。

统计“没有商品的供应商也显示为 0”必须 LEFT JOIN，并 COUNT(右表主键)，不能用 COUNT(*)。

5.6 子查询与 EXISTS ★★★★☆

  • 标量子查询返回一个值，可配 =、>。
  • 多行子查询通常配 IN。
  • EXISTS只判断相关行是否存在；NOT EXISTS很适合“没有学过/没有订单/没有匹配记录”。
  • NOT IN子查询若含 NULL可能导致结果意外为空，反向存在性优先考虑 NOT EXISTS。

5.7 日期查询 ★★★★★

使用“月初闭区间、下月月初开区间”能包含本月所有带时分秒的数据，也有利于使用日期索引。不要写 created_at <= '本月最后一天'而漏掉当天非零时间。

5.8 增删改、DDL 与事务 ★★★☆☆

命令 删除内容 表结构 自增计数 WHERE
DELETE 指定/全部数据行 保留 通常不重置 可用
TRUNCATE 全部数据行 保留 通常重置 不可用
DROP 表及数据 删除 表不存在 不可用

事务用于维护数据一致性：BEGIN开始，COMMIT提交，ROLLBACK回滚。

A.1 软件运行环境与 Web 基础

  • C/S 架构：客户端承担较多逻辑，通常需要安装与升级；测试时关注客户端版本、操作系统兼容、网络中断和服务端交互。
  • B/S 架构：通过浏览器访问；测试时重点关注浏览器兼容、分辨率、前后端交互、Cookie/Session、URL、缓存和网络异常。
  • URL 基本结构：协议://主机:端口/路径?查询参数#片段。例如 https://example.com:443/goods?id=1。
  • 常用端口：HTTP 80、HTTPS 443、SSH 22、MySQL 3306。实际项目以部署配置为准。
  • HTML 表单：输入框、单选、复选、下拉框、文件上传和提交按钮都需要检查默认值、必填、长度、格式、重复提交及异常输入。
  • 前端校验不能替代后端校验：前端校验改善体验，后端校验保障数据与安全；接口请求可绕过页面校验。

A.2 网络基础

  • 集线器：收到数据后向其他端口广播，冲突域较大。
  • 交换机：根据 MAC 地址表转发局域网数据帧，每个端口可形成独立冲突域。
  • 路由器：根据 IP 和路由表在不同网络之间转发数据包，并隔离广播域。
  • 常见拓扑：星型便于管理、单点链路故障影响局部；总线型结构简单但主干故障影响大；环型节点依次连接；网状拓扑冗余高但成本高。
  • 排查思路：先判断本机、局域网、网关、DNS、目标服务器还是应用服务异常，再结合连通性、端口、日志和进程状态定位。

A.3 Linux 与测试环境

  • 查看文件/日志：理解按关键字、时间、行数定位错误信息的思路；考试常考日志分析目的，而非只背命令。
  • 进程与端口：环境无法访问时，依次确认服务进程、监听端口、防火墙、配置、依赖服务和日志。
  • 权限：区分文件所有者、用户组、其他用户的读/写/执行权限；权限不足可能导致启动、上传、写日志或读取配置失败。
  • 部署后验证：服务启动成功后，还应做端口检查、页面或接口检查、数据库连接检查和核心业务冒烟测试。
  • 环境记录：记录系统版本、应用版本、数据库版本、浏览器、配置、账号和测试数据，保证缺陷可复现。

A.4 进制与数据表示

  • 二进制转十进制：按位权展开，例如 1011₂ = 1×2³ + 0×2² + 1×2¹ + 1×2⁰ = 11₁₀。
  • 十进制转二进制：整数连续除 2 取余，余数倒序排列。
  • 二进制与十六进制：从右向左每 4 位一组，例如 1111 1010₂ = FA₁₆。
  • 测试中的应用：颜色值、权限位、掩码、编码和底层数据可能使用十六进制或二进制表示。

A.5 HTML/JavaScript 作业对测试设计的启示

  • 页面行为可能同时受 HTML 属性、JavaScript 校验、接口规则和数据库约束影响，应分层验证。
