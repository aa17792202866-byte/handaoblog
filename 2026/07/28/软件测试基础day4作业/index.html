软件测试基础day4作业

1. 缺陷的类型（即：判断软件缺陷的规则）

  •   软件未实现产品规格说明书（需求）标明的功能。

  •   软件出现了规格说明书指明不会出现的错误。

  •   软件功能实现了规格说明书未定义的内容。

  •   软件未达到规格说明书虽未指出但应达到的目标（即隐含需求）。

  •   测试员认为软件难以理解、不易使用、运行速度缓慢，或者最终用户认为体验不好。

2. 描述缺陷的要素

在缺陷管理工具（如禅道）中，描述一个缺陷通常包含以下要素：

  •   基本信息：所属产品、所属项目、所属模块、影响版本、当前指派、截止日期、BUG类型、操作系统、浏览器类型。

  •   核心要素：BUG标题（描述位置及问题内容）、严重程度、优先级。

  •   具体内容：

    -   操作步骤（序号编排）

    -   实际结果

    -   预期结果

    -   截图或附件（UI类需红框标识，功能类建议视频）

  •   接口类 Bug 额外要素：

    -   接口地址

    -   请求方式

    -   传入参数

    -   接口返回数据

3. 描述缺陷的状态

  •   新的（New/激活）：缺陷的初始状态。

  •   已确认（Confirmed）：经分析确定为 BUG。

  •   已打开（Open）：开发人员开始修改缺陷。

  •   已修复（Fixed/已解决）：开发人员修改完毕。

  •   已关闭（Closed）：回归测试通过。

  •   再打开（Reopen/激活）：回归测试失败，需重新修改。

  •   延期（Postpone）：推迟修改。

  •   被拒绝（Rejected/不予解决）：开发认为不是程序问题。

4. 描述缺陷的生命周期（即：缺陷的管理流程）

一般流程：

    创建（激活） -> 确认（已确认） -> 解决（已解决） -> 关闭（已关闭）

流程说明：

  1.  测试人员发现并创建 BUG（状态为激活）。

  2.  开发或管理人员确认 BUG 并指派给对应开发人员。

  3.  研发人员解决问题后，将状态改为”已解决”，并指派回测试人员。

  4.  测试人员回归测试，若通过则关闭，若未通过则重新激活（Reopen）。

5. 描述缺陷的严重程度及划分标准

  1.  致命缺陷：导致系统崩溃、宕机、无法登录、经常闪退或主流程应用模块无法启动，阻碍开发和测试。

  2.  严重缺陷：主要功能部分丧失、数据不能保存，或系统提供的服务受到明显影响。

  3.  一般缺陷：次要功能未实现，但不影响正常使用，或由于兼容性导致界面变形、图片不显示。

  4.  轻微缺陷：不影响功能的易用性问题、文字错误、操作建议或界面美观问题。

6. 描述常见的缺陷管理工具

  •   商用工具：HP ALM、IBM Rational ClearQuest。

  •   国产工具：禅道（Zentao）。

  •   开源/共享软件：Jira、Bugzilla、Mantis。

7. 如何写好一个高质量的缺陷？

书写高质量缺陷报告应遵守 “5C”准则：

  •   准确（Correct）

  •   清晰（Clear）

  •   简洁（Concise）

  •   完整（Complete）

  •   一致（Consistent）

其他要求：

  •   单一性：一个报告只针对一个缺陷。

  •   步骤清晰：用序号编排复现步骤，确保缺陷可再现。

  •   标题简明：采用”位置 + 操作 +

    结果”的格式，字数一般不超过20字，且无错别字。

  •   客观事实：只描述事实，不做评价，不进行人身攻击。

  •   附件辅助：提供截图、录屏或日志，直观定位问题。

8. 提了一个 bug，开发不认可怎么办？

  •   提前沟通：与开发人员进行沟通协商解决。

  •   确认需求：与产品经理或设计人员确认是否符合原始设计。

  •   协助复现：如果是无法重现，测试应尝试多次测试确定场景，或联系开发当面复现。

  •   坚持激活：若无法接受解决方案，测试有权重新激活 BUG。

  •   会议讨论：若双方僵持不下，可在发版前会议上进行讨论，由相关负责人裁决处理方案。

9. URL 是什么？由哪几部分构成？

URL（Uniform Resource Locator）是统一资源定位符。

组成部分：

  •   协议（Protocol）：如 http、https。

  •   域名/主机名（Domain/Host）：如 test.app.enjoybuy.vip。

  •   端口（Port）：默认 http 为 80，https 为 443（通常可省略）。

  •   路径（Path）：如 /store/api/v1.0.0/content/getContentDetail。

  •   查询参数（Query）：以 ? 开始，如 content_id=91&type=2。

10. OSI 模型与 TCP/IP 协议模型

OSI 七层模型

物理层、数据链路层、网络层、传输层、会话层、表示层、应用层。

TCP/IP 四层模型

网络接口层、网络层（IP）、传输层（TCP/UDP）、应用层（HTTP/FTP等）。

11. TCP/IP 协议中的三次握手、四次挥手

三次握手（建立连接）

客户端发送 SYN → 服务端返回 SYN+ACK → 客户端返回 ACK。

四次挥手（断开连接）

主动方发送 FIN → 被动方返回 ACK → 被动方发送 FIN → 主动方返回 ACK。

12. 测试用例优先级划分标准

  •   高：核心功能的正向用例。

  •   中：核心功能的反向用例、次要功能的正向用例。

  •   低：次要功能的反向用例、易用性、容错、异常场景用例。
