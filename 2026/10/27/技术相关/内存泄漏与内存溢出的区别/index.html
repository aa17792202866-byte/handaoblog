内存泄漏与内存溢出：区别、图解与测试思路

内存泄漏和内存溢出经常一起出现，但含义不同：泄漏是本该释放的内存一直被占用；溢出是程序需要申请内存时，无法获得足够的可用内存。 本文结合内存占用条和使用趋势图，记录它们的区别及测试思路。

一、先分清两个概念

内存泄漏（Memory Leak）

程序申请的内存已经不再需要，却由于程序问题没有被释放或回收，导致这部分空间继续被占用。

在 C/C++ 等手动管理内存的场景中，可能是忘记释放，或者丢失了指向已分配内存的指针。在 Java、JavaScript 等有垃圾回收机制的环境里，也可能是对象已经没有业务用途，却仍被长期存活的容器、监听器或其他引用持有，因而无法回收。

垃圾回收主要判断对象是否仍然可达，并不知道业务是否还需要它；现代 JavaScript 引擎也不会仅仅因为对象之间存在循环引用就一定泄漏。参见 MDN：内存管理。

内存溢出（Out of Memory，OOM）

本文中的“内存溢出”指内存不足或分配失败。程序需要更多内存，但受到堆大小、进程地址空间、容器限额或系统资源等约束，无法满足申请。

不同环境的表现不同，例如抛出内存不足错误、分配函数返回失败，或进程因内存限制被终止。它也不同于“缓冲区溢出”：后者是读写越过缓冲区边界的问题。

OOM 不等于已经证实存在泄漏。 例如 Java 的 OutOfMemoryError: Java heap space 也可能只是堆配置不足；错误还可能涉及本地内存等资源。参见 Oracle：理解 OutOfMemoryError。

对照记忆

对比项 内存泄漏 内存溢出
核心问题 不再需要的内存仍被占用 新的内存需求无法满足
关注点 内存是否正确释放或回收 可用空间能否满足申请
时间特征 可能长期、逐步累积 可能突然发生，也可能累积后发生
常见线索 相同负载下，回收后的占用基线持续抬升 内存不足日志、分配失败、进程退出等
关系 持续累积可能最终导致 OOM 可能由泄漏导致，也可能由正常需求过大导致

可以把内存看作仓库：已经不用的货物一直不清理，是泄漏；新货进来时没有足够空间，是 OOM。仓库也可能没有废弃货物，只是这一批新货太大。

二、用进度条理解内存占用

假设程序可用内存上限为 1000MB。图中用绿、橙、红进度条对比正常使用、内存泄漏和内存不足。

  • 正常情况：任务使用内存后，释放资源或使对象具备被回收条件，后续占用能回落到合理范围。
  • 泄漏情况：不再需要的对象或分配块没有正确清理，重复运行后占用可能越来越高。
  • OOM 情况：新的申请无法满足。图中的满条只是便于理解的示意，不是 OOM 的判断条件。

图中按 1000MB 的总容量演示。若采用二进制单位，应写作 1 GiB = 1024 MiB。

即使还有 200MB 可用，下一次需要申请 300MB，也可能失败；另外，堆、进程与容器的限制可能不同。因此，不能要求监控面板必须先显示“100%”，才能认定发生了 OOM。

三、从软件测试角度看趋势

假设使用 JMeter 对网站施加持续负载，应同时监控被测服务端进程，而不只观察 JMeter 客户端占用。

图中横轴为运行时间，纵轴为内存使用率。它是教学示意图，不是一次真实压测的监测记录。

蓝线表示相对稳定的波动：请求到来时分配内存，任务结束或垃圾回收后有所回落。绿线表示持续抬升的占用，应进一步排查是否存在泄漏。

单看绿线不能下结论：缓存预热、业务数据增长、并发增加以及运行时保留内存，都可能造成上涨。观察时应固定指标口径，例如始终比较同一进程的已用堆占最大堆比例，不要把它与系统总内存占用混在一起。

一个可执行的测试思路

  1. 记录环境与指标：服务版本、内存限制、并发数、请求比例，以及堆使用量、进程 RSS 等。RSS 是进程驻留物理内存，不能直接当作存活对象大小。
  2. 完成预热：让连接池、常用缓存和运行时初始化趋于稳定，再记录基线。
  3. 重复同样的业务周期：在负载尽量一致的前提下，多轮执行查询、上传、打开关闭页面等操作，轮间留出空闲观察期。
  4. 比较回落后的基线：对托管堆，重点看可比较的垃圾回收后存活对象量，是否随轮次持续增长；不要只比较分配峰值。
  5. 保留定位证据：结合堆快照、对象数量、引用链或原生内存分析，确认哪些不再需要的资源仍被保留。采集方式应适合当前运行环境，并考虑其性能开销。
  6. 修改后复测：用相同负载和指标比较修复前后，判断增长是否消失、占用是否趋于稳定。

如果发生 OOM，另外记录错误类型、时间点、当时负载与资源限额；若进程直接退出，应结合退出信息和系统或容器事件排查。一次截图或一次峰值不足以说明根因。

六、面试时可以这样回答

内存泄漏是程序不再需要的内存没有被正确释放或回收，内存溢出是程序申请内存时无法获得足够空间。泄漏累积可能导致溢出，但溢出也可能由一次申请过大、并发过高或内存限制过小引起。测试时会在稳定负载下观察内存回落后的基线，并结合堆快照和引用链定位，不能只凭内存曲线持续上涨就认定泄漏。
