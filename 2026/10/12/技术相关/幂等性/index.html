幂等性

Gemini

幂等性（Idempotency）是一个计算机与系统设计概念，简单来说： 任意多次执行同一个操作，对系统产生的影响均与一次执行的影响相同。

例如：

  • 具有幂等性的操作 ：将用户的账户状态改为“已激活”。你点一次是激活，点一百次结果也是激活，状态不会变来变去。
  • 不具备幂等性的操作 ：账户余额“加 100 元”。点一次加 100，点三次就加了 300，产生了重复累加的影响。

它在 Postman、MySQL 还是哪里？

幂等性 不属于某一个单一的软件 ，而是一个 系统架构和后端开发的设计规范 。它会涉及到你提到的这两个地方，以及后端代码：

  1. 后端代码与架构（核心实现层）
    • 幂等性主要靠后端逻辑来保证。常见的实现方式包括：
      • 唯一请求 ID（Token 机制） ：前端每次请求带一个唯一 ID，后端处理过后记录下来，如果收到相同 ID 的第二次请求直接返回上次的结果。
        - 状态机判断 ：比如订单已经是“已支付”，再次收到支付请求直接跳过。
  2. MySQL（数据持久层）
    • MySQL 是辅助实现幂等性的重要工具。最常用的方法是给关键字段加上 唯一索引（Unique Index） 。
      • 例如：如果业务要求一个用户只能领一张优惠券，可以在数据库的“用户ID+优惠券ID”上建立唯一索引。这样哪怕前端重复发送了请求，MySQL 也会直接拦截第二条相同的插入操作，报错或拒绝，从而保证数据不重复。
  3. Postman（测试验证层）
    • Postman 既不是幂等的创造者，也不是实现者，而是用来 验证 幂等性的 测试工具 。
      • 怎么用 ：你在开发完一个接口（比如下单或支付接口）后，在 Postman 里面连续快速点击几次 Send 按钮。如果系统设计了幂等性，数据库里应该只有一条记录，不会出现重复扣款或生成多条订单；如果没有做幂等性，就会出现数据重复或报错。

后端实现幂等性主要有以下几种经典方案，你可以根据具体的业务场景（如支付、下单、表单提交）来选择：

1. 数据库唯一索引（适合：新增插入操作）

  • 原理 ：利用数据库的唯一性约束来防止重复数据写入。
  • 实现方式 ：
    • 比如用户领取优惠券，设计表时将 user_id 和 coupon_id 设为 联合唯一索引 （Unique Index）。
      • 当用户第一次点击领取时，数据成功写入。
      • 当用户重复点击发送第二次请求时，数据库会抛出主键/唯一索引冲突异常（如 MySQL 的 Duplicate entry ）。后端捕获该异常后，可以直接返回“领取成功”或友好提示，而不会插入重复数据。

2. Token 机制 / 防重令牌（适合：表单提交、支付下单）

  • 原理 ：每次提交前先向服务端申请一个“一次性凭证”，提交时验证并销毁它。
  • 实现方式 ：
    1. 获取 Token ：用户打开提交页面时，后端生成一个全局唯一的 Token（比如 UUID），存入 Redis 中并设置过期时间（如 5 分钟）。
      1. 携带 Token 提交 ：前端提交表单时，将这个 Token 作为请求头或参数传给后端。
      2. 后端校验与删除 ：后端收到请求后，使用原子操作（如 Redis 的 DEL 或 Lua 脚本）去 Redis 中检查并删除这个 Token：
      • 如果删除成功（Token 存在），说明是第一次请求，放行并执行业务。
        - 如果删除失败（Token 不存在或已被删），说明是重复提交，直接拒绝。

3. 状态机幂等（适合：状态流转、订单支付）

  • 原理 ：通过流转条件限制，确保同一个状态转换只发生一次。
  • 实现方式 ：
    • 订单通常有状态： 待支付 -> 已支付 -> 已发货 。

      • 如果订单已经是 PAID 状态，再次执行这条 SQL 时， 影响行数（Affected Rows）为 0 。后端可以通过判断影响行数是否大于 0 来决定是否执行后续的加积分、发货等逻辑。

4. 分布式锁（适合：高并发秒杀、资金扣减）

  • 原理 ：在并发场景下，通过加锁保证同一时间只有一个相同业务标识的请求在执行。
  • 实现方式 ：
    • 客户端请求带上唯一的业务流水号（如 order_no ）。
      • 后端使用 Redis 分布式锁（如 SETNX 或 Redisson），以该流水号作为 Key 加锁。
      • 获取到锁的请求继续执行业务，未获取到锁的请求直接返回“系统处理中”或重复请求提示，执行完毕后释放锁。
