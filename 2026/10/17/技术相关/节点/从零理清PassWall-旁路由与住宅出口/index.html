从零理清 PassWall：旁路由、住宅出口、1070 与 1081 和自动切换

这篇笔记整理一次 iStoreOS 配置实践：先安装 PassWall，再让多个 VLESS 节点作为住宅 SOCKS5 的前置线路，并向局域网提供两个不同出口的代理端口。重点是解释每项配置为什么这样填，而不只是照着操作。

记录环境是 iStoreOS 25.12.5、PassWall 26.10.16-r2。菜单名称以这次界面为准，后续版本可能变化。本文保留实际使用的局域网地址与端口，省略订阅令牌、UUID、代理账号、密码和公网出口地址。照搬到其他网络时，需要替换局域网地址。

1. 先记住实际配置的全貌

旁路由地址是 192.168.31.165，它提供两个 SOCKS5 入口：

其中“住宅出口节点”是路由器上的一份配置，不是流量先到住宅服务器再到 VLESS。实际远端连接顺序始终是：先经过 VLESS，再由住宅代理访问网站。

2. 地址、端口、节点、核心分别是什么

可以把旁路由想成一座有多个服务窗口的建筑：IP 地址找到建筑，端口找到窗口，窗口后面的规则决定怎么办理请求。

概念 在本次配置中的含义
IP 地址 192.168.31.165 是局域网中旁路由的位置
端口 1070 和 1081 是旁路由上两个不同的服务入口
监听 某个程序正在等待其他设备连接这个端口
节点 一份连接配置，包括协议、远端地址、端口、认证及前置代理等
Xray 核心 真正执行代理协议和连接转发的程序
PassWall 管理核心、节点、路由和规则的配置界面及配套脚本
出口 IP 目标网站看到的发起连接一方的公网地址

1070 并不天生代表住宅，1081 也不天生代表普通代理。它们的用途由绑定的节点决定。 如果以后修改主页面的代理节点，1070 对应的出口也会变化。

同样，路由器的本地入口端口，与住宅代理商提供的远端端口，是两件事：

手机不需要填写住宅代理商的账号密码，是因为认证由路由器上保存的住宅节点配置完成。这不代表所有 SOCKS 服务都不需要认证。

3. VLESS、XHTTP、TLS 和 SOCKS5 的关系

这次前置节点使用 VLESS + XHTTP + TLS：

部分 作用
VLESS 代理协议，包含用户身份等连接信息
XHTTP 传输方式，决定代理数据如何通过 HTTP 相关连接传送
TLS 保护这段连接，并验证对端证书身份
SNI TLS 连接中的服务器名称，需要与服务端配置对应
Host、Path、Mode XHTTP 相关参数，需要按节点提供的信息填写
ECH、Extra 链接可能附带的额外配置，导入后应检查是否完整保留
SOCKS5 客户端请求代理服务器代为连接目标的一种协议

SOCKS5 本身不提供传输加密；HTTPS 网站的 TLS 是另一个层次，不能与代理协议混为一谈。前置 VLESS 也不会自动把整条链路变成一种新的协议。

PassWall 页面可以打开，并不代表 Xray 核心已经安装。本次曾出现链接导入后没有有效节点的情况，后来检查发现系统未安装 xray-core。这是一条排查线索，不能据此断言所有导入失败都由缺核心引起。

4. 什么是前置代理和住宅落地

“前置代理”解决的是：当前节点通过哪条代理线路去连接它自己的远端服务器。

在住宅节点里选择 VLESS 作为前置后：

VLESS 承担前面的连接线路，住宅代理是最后访问目标网站的代理，所以网站看到住宅代理的出口。

本次测试中，1070 返回的公网 IP 与填写的住宅代理地址一致，但这只是这一次结果。代理商也可能使用网关地址、轮换出口或会话绑定机制，连接地址与最终出口 IP 不一定永远相同。仅凭 IP 相同，也不能独立证明其运营商分类一定是住宅。

5. 本次三个关键位置应该怎样对应

5.1 主页面：选择住宅出口，提供 1070

字段 本次设置
主开关 开启
代理节点 Xray Socks：住宅出口
节点 Socks 监听端口 1070
节点 Socks 本机监听 局域网其他设备要连接时不勾选

因此局域网软件连接 192.168.31.165:1070，会使用住宅节点。

5.2 住宅节点：把 1081 当作前置入口

字段 本次设置
类型 Xray
协议名称 Socks
地址、端口、用户名、密码 住宅代理商提供的信息
链式代理 前置代理节点
前置代理节点 Socks 配置 [1081端口]

这里选本机 1081，是为了复用它的 VLESS 自动切换能力。

5.3 下方 Socks 配置：1081 负责选择 VLESS

字段 本次设置
启用 开启
节点 一个已验证可用的主用 VLESS
Socks 监听端口 1081
HTTP 监听端口 0，表示不启用 HTTP 入口
本机监听 因为局域网设备也要用，所以不勾选
自动切换 开启
后备节点添加方式 手动
备用节点列表 其他可用 VLESS，不包含住宅出口

保存配置后，还要在概览页面“保存并应用”。

避免循环：1081 的主节点和备用列表都不能选住宅出口。 否则住宅出口依赖 1081，而 1081 又依赖住宅出口，连接无法正常建立。

如果不需要局域网直接使用 1081，可以将它限制为本机监听，1070 仍可通过本机连接它。这里保留局域网访问，是本次使用需求，而不是住宅链式代理的必要条件。

6. 为什么两个端口都能受益于自动切换

自动切换实际配置在 1081 入口上。

故障位置 1081 的表现 1070 的表现
当前 VLESS 不通，备用可用 检测后切换到备用 后续连接借用切换后的前置线路
住宅代理不通、到期或认证失败 可能仍正常 仍失败，备用 VLESS 无法替代住宅服务
所有 VLESS 都不通 失败 前置线路不可用，通常也失败
住宅 IP 被某个网站拒绝 普通出口可能仍能访问 更换前置未必有用，最终出口没有改变

检测用的是 Google 等探测网址，并不代表对每个目标都做了健康检查。某网站单独故障，也未必触发切换。

本次建议的检测值为 60 秒一次、超时 5 秒、重试 2 次，作为减少误判的起点，并非所有网络的最优值。实际切换时间还受检测脚本与节点数量影响，不能简单保证几秒内恢复。

“恢复切换”决定主节点恢复后是否切回。暂不勾选可以减少不稳定时的来回切换。已有连接可能中断，切换主要帮助重新建立的连接，并不是无缝迁移。

7. 自动切换、负载均衡、分流不是一回事

功能 回答的问题 例子
自动切换 当前节点坏了怎么办？ A 不通后改用 B
负载均衡 多条可用线路如何分担连接？ 不同连接分别交给 A、B
分流 访问什么目标时走哪里？ 国内直连，某些网站走住宅，其余走 VLESS
链式代理 同一个连接依次经过哪些代理？ VLESS → 住宅 SOCKS5

“Xray 分流总节点”本身是一份按规则选择出口的配置，不是额外的一台服务器，也不会因加入多个节点就自动故障切换。

本次已经使用 Socks 配置里的自动切换，不需要再开启 HAProxy 负载均衡。HAProxy 装着但未运行，不影响当前这套配置。也不要把 VLESS 和住宅节点放进同一个轮询列表：它们原本是串联关系，并不是两个等价的最终出口。

单次下载一般也不会因为负载均衡而自动叠加两条线路的带宽。

8. 其他设备使用旁路由的两种方式

8.1 在软件里明确填写 SOCKS5

想使用住宅出口时：

项目 填写
类型 SOCKS5
服务器 192.168.31.165
端口 1070
用户名、密码 本次入口未配置认证，留空
通过代理解析域名 软件提供时开启

想直接使用 VLESS 出口，就把端口改为 1081。

这种方式只作用于确实采用该代理设置的软件或连接。手机 Wi-Fi 页面中的普通“HTTP 代理”不能直接当成 SOCKS5 配置；本次 1081 的 HTTP 端口为 0，也没有启用对应 HTTP 服务。

8.2 修改设备网关和 DNS

这属于通过旁路由转发，并由 PassWall 透明代理规则处理，不需要在设备上填写 1070 或 1081。

项目 本次网络中的设置
设备 IP 保留设备自己的 192.168.31.x，不能与旁路由或其他设备重复
子网掩码 / 前缀 本次按 255.255.255.0 / 24 配置，其他网络应沿用实际值
IPv4 网关 192.168.31.165
DNS 192.168.31.165，前提是旁路由正在提供可访问的 DNS 服务

改网关只是把相应流量送到旁路由，并不保证所有应用、所有协议都会走住宅代理。还要看 IPv6 路由、访问控制、分流规则、TCP/UDP 支持等。

DNS 负责查询地址，网关负责转发数据。只改 DNS 不等于建立代理。

socks5h 表示让 SOCKS 代理端处理目标域名解析。服务返回出口 IP 后可能直接与终端提示符相连，这是因为响应不一定包含换行。

本次两个命令均返回公网地址：1081 是普通出口，1070 与住宅代理配置地址一致。这验证了当时两个入口的 HTTPS/TCP 请求可用，没有验证 UDP、所有 App、IPv6 或故障切换全过程。

现象 优先排查
1081 成功，1070 失败 住宅账号、端口、服务状态，以及住宅节点的前置设置
两个都失败 当前 VLESS、Xray 日志及网络连通性
路由器本机成功，其他设备 SOCKS 失败 本机监听限制、LAN 防火墙、客户端填错代理类型或端口
浏览器成功，App 失败 App 的 TCP/UDP、QUIC、IPv6、DNS 和分流差异

“端口正在监听”只代表程序在等待连接；“TCP/UDP 运行中”只代表相关进程状态。主页网站测试也只是一种探测。本次曾出现主页探测失败、但两个端口实际请求均成功的情况，不能单凭一块状态卡判断整条线路。

10. 浏览器能访问，但电视或手机 App 不行

本次曾观察到浏览器能打开 Google 和 YouTube，但 App 不能使用。该问题在记录中没有完成定位，不能写成已经修好。

可能原因包括：

  • App 使用 UDP/QUIC，而住宅 SOCKS5 服务没有可用的 UDP 转发能力。
  • 只修改 IPv4 网关，IPv6 仍使用另一条路径。
  • 浏览器使用的目标域名、DNS 或传输方式与 App 不同。
  • PassWall 的访问控制或分流规则没有覆盖相关流量。

可逐项对照测试：先确认同一设备、同一网络，关闭设备自身 VPN 以免混淆；核对 App 的错误日志；再检查 IPv6 和 UDP。屏蔽代理 UDP 443 可以作为促使部分 QUIC 应用回退 TCP 的实验，但并非所有 App 都会回退，也不能直接当成通用修复。

12. 最后用四个问题检查自己是否理解

为什么 1070 是住宅出口？ 因为它绑定了住宅节点；住宅节点借助 1081 去连接住宅服务器。

为什么 1081 是普通出口？ 因为它绑定的是 VLESS，直接连接它就不会再经过住宅节点。

为什么两者都能用备用 VLESS？ 因为自动切换发生在 1081，而 1070 也依赖这个入口；住宅服务本身并没有备用。

为什么当前不需要负载均衡？ 因为目标是前置故障后切换，Socks 自动切换已经承担这个任务。

局域网共享这些入口时，仅允许可信网络访问，不在主路由上向公网转发未认证的代理端口。文章或截图也不要包含订阅令牌、UUID 和代理密码。
