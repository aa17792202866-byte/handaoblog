小说网站搜索接口测试项目复盘

我把搜索需求拆成可验证的规则，先准备请求条件和独立预期，再用 Postman 校验响应，并把需要联动的请求按顺序串起来。

本文对照《韩瑞轩-小说网站最终版.json》和《小说搜索、分类筛选与搜索结果接口.md》整理。关于集合脚本的结论来自导出文件的静态分析，未发送请求或修改源文件。

一、用五步讲清楚整个项目

步骤 项目做法
测什么 以 /book/searchByPage 为主，覆盖关键词、组合筛选、分页、排序、时间边界和异常输入，再覆盖分类、详情、章节和书架等关联接口。01_默认回归 放常规检查和联动，02_需配置数据 放依赖样本或账号的场景，03_探索请求 用来观察实际行为，榜单和会写数据的请求各自独立。
数据怎么准备 请求输入包括关键词和日期，例如 API-034 在 Params 中直接传「红」，API-046 从 fixtures.zeroWords.params 读取关键词。独立预期来自数据库核对，例如 fixtures.orUnion.ids 和 recentBookExpectedTotal。联动变量由上游响应提供，例如 qaCat、qaBook 和 qaChapter。
请求怎么发 API-005 搜索首页，选一本有章节的书，保存书籍 ID、书名、作者和分类。API-023 用 qaBook 查详情并核对字段，再把最新章节 ID 保存为 qaChapter。API-026 使用这两个 ID 查询章节摘要。
结果怎么判断 JSON 用例通常依次检查 HTTP 状态、业务码和业务数据。总数正确时仍需核对 ID，因为漏书和多返回的书可能正好抵消。API-021 的非数字页码预期是 HTTP 200 和 HTML 错误页标题。API-057 只记录状态并跳过业务断言，API-066 在最终版中已添加实际断言。
失败怎么定位 前置脚本提示缺少 qaCat 或 fixtures.zeroWords 时，先查配置和依赖，请求可能尚未发出。如果 HTTP 状态和业务码都通过，但 ID 或总数有误，就检查实际请求参数和响应。例如 API-047 修改时间下限后，命中由 1 本变成 2 本，需要按新条件重查数据库，再判断是更新预期还是排查接口。

二、四组代表用例

API-034 · 书名或作者 OR 搜索与去重

  • 样本准备。同一个关键词应覆盖只匹配书名、只匹配作者名、两边都匹配三类书。前两类能发现只搜索一个字段的问题，第三类能发现同一本书被返回两次的问题。
  • 请求与断言。Params 直接传关键词「红」，第一页最多取 100 条。后置脚本读取 fixtures.orUnion.ids 中的 8 个预期 ID，先比较总数，再将实际和预期 ID 分别排序后比较。
  • 通过条件。这批样本的数量和具体书籍都正确即可，返回顺序可以不同。三种命中类型是否齐全，需要在准备样本时独立确认。

API-046 · 排除零字数书籍

  • 样本准备。用「命」同时匹配零字数书和正常书，预期 ID 只填正常书。只有确认零字数书符合其他搜索条件，才能用它验证字数过滤。
  • 请求与断言。前置脚本检查 fixtures.zeroWords 的格式，把 params.keyword 加入搜索请求。后置脚本核对总数和具体 ID。
  • 导入后的配置。最终导出文件缺少 zeroWords，重新导入后要补齐样本配置，否则前置脚本会拦住请求。

API-054 / 055 · 跨页完整性

  • 样本准备。两页使用相同的关键词、页大小和字数排序。导出文件使用关键词「修仙界」，每页 2 条，配置了 3 个独立预期 ID。
  • 请求与断言。054 请求第 1 页，将查询设置、总数、本页 ID 和最后一本书保存到 qaCrossFirst。055 请求第 2 页，检查两页查询设置和总数一致，再合并两页 ID。
  • 通过条件。有独立预期时，合并后的 ID 必须和预期完全一致，可以发现漏书、重复或错书。预期 ID 留空时，执行页码、页大小、条数和两页一致性等基础检查。只有两页都有数据且边界字数不相等时，才额外检查跨页去重和边界降序。

API-066 · 页面未提供的更新时间周期

  • 样本准备。页面提供 3、7、15、30 天。接口用例直接传 updatePeriod=1，测试过去 24 小时的筛选。用数据库独立统计这个时间范围内字数大于 0 的书籍数量。
  • 请求与断言。请求传 updatePeriod=1&limit=1。后置脚本读取 recentBookExpectedTotal，与 data.total 比较。预期总数为 0 时本页应为空，预期总数大于 0 时本页应有 1 条。例如总数是 98，limit=1 仍只允许本页返回 1 条。
  • 导入后的配置。导出文件中的 recentBookExpectedTotal 为空，需要填入当次数据库查询结果。

API-071 使用 POST /book/addVisitCount 增加访问量。最终版中前置保护已被注释，后置脚本只检查 HTTP 状态和业务码。要验证访问量确实增加 1，需要对照写入前后的计数。「无收费书籍时返回状况」是手工观察请求，集合没有配置自动断言。

三、约 2 分钟的面试口述稿

我这个项目主要测小说网站的搜索接口。我先根据接口规则拆场景，比如关键词命中、组合筛选、分页排序、时间边界和异常参数。然后在 Postman 里把默认回归、需要准备数据的场景、探索请求和会写数据的请求分开，这样知道哪些能直接跑，哪些要先准备条件。

准备数据时，我会区分请求输入和预期结果。比如测书名或作者搜索，我用同一个关键词准备只命中书名、只命中作者、两边都命中的样本。关键词用来发请求，数据库核对出来的书籍 ID 放在集合变量里当预期。收到响应后，我先看 HTTP 状态和业务码，再比较总数和具体 ID。因为数量一样，也有可能漏了一本，又多返回了一本。

我还做了搜索到详情、再到章节摘要的联动。先从搜索结果取书籍 ID，查详情时核对书名、作者和分类，再把详情返回的最新章节 ID 保存下来，给下一条摘要请求用。这几条有数据依赖，所以要按顺序执行。

遇到失败，我先看请求到底有没有发出去。前置脚本缺变量，就先查配置。如果 HTTP 和业务码都通过，但数量或 ID 不对，我会检查实际发送的参数，再用数据库按同样的条件查一遍。像最近 24 小时更新这种会随时间变化的用例，我用当次数据库查出的数量做预期。这样能判断是接口行为有问题，还是测试数据已经变化。

四、关键词复述提纲

  1. 范围。搜索为主，覆盖关键词、筛选、分页、排序、异常和关联接口。
  2. 数据。Params 放请求条件，fixtures 存样本预期，上游响应提供联动变量。
  3. 执行。按依赖顺序跑，典型链路是搜索 → 详情 → 章节摘要。
  4. 断言。先看 HTTP 状态，再看业务码，最后核对总数、具体 ID 或关键字段。
  5. 排查。先确认请求有没有发出，再核对参数、响应和数据库预期。

五、面试常见追问

追问 参考回答
预期数据从哪里来？ 用数据库按测试条件独立核对。固定样本存书籍 ID，最近 24 小时这种动态场景填本次查到的总数。
为什么 HTTP 200 还可能失败？ HTTP 200 表示请求在 HTTP 层得到成功响应。业务码仍可能报错。即使业务码也是 200，返回的书也可能有误。
怎么证明零字数过滤生效？ 让零字数书和正常书都匹配同一个关键词，再验证只返回正常书。这样可以确认被排除的书满足其他搜索条件。
分页怎么验证没漏、没重复？ 保存第一页 ID，与第二页合并后对照独立预期 ID。两页总数相同也可能漏书。
数据库变了，断言怎么维护？ 先按实际请求条件重查数据库，确认是样本变化后，再同步更新请求参数和预期。例如改了时间下限，就按新下限重查符合条件的 ID。

六、集合的三个局限

  1. 部分场景依赖外部数据。API-046 依赖库中确实存在匹配的零字数反例，API-066 依赖当次数据库预期。需要在执行前确认这些条件。
  2. 跨页检查只覆盖选定的两页。独立预期为空、排序边界并列，或数据在两次请求之间变化时，能得出的结论更有限。
  3. 写入断言只覆盖成功响应。API-071 的访问量是否增加 1，需要用写入前后的计数确认。
